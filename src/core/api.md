# belay Core API contract, build 1

Version 1, 2026-09-08. Owned by the lead; only the lead edits it. Every agent codes against it. Governing records: ADR 0002 (store), 0004 (spawn), 0007 (checkpoint, briefing), 0010 §2 (proof columns), §4 (authority). Where this file and a record differ, tell the lead; do not resolve it locally.

## 1. Modules and boundaries

| Module | Exports | Runs in |
|---|---|---|
| `src/core/index.cjs` | `openCore(opts) → Promise<Core>`, `CoreError`, `pipeName(dataDir)`, `pidAlive(pid)` | every adapter, both roles |
| `src/run/index.cjs` | `createRunManager({ core, dataDir, runId, paths?, compactAtTokens? }) → RunManager` (`compactAtTokens`, default `null`: the `compact_at_tokens` run lever, ADR 0007 decision 3, set by the adapter's `--compact-at`; null leaves every launch, settings file and stdin exactly as before); `paths = { mcpBinary?, claudeExe?, codexExe?, userSettings?, adapterPid? }`; `mcpBinary` defaults to `src/mcp/belay-mcp.cjs` resolved from `src/run`, `claudeExe`/`codexExe`/`userSettings` are test seams defaulting to the host binaries and `~/.claude/settings.json`, `adapterPid` overrides the pid every row this manager writes claims as `adapter_pid` (default `process.pid`; build step 6f-2, a test seam for giving two managers distinct identities in one OS process) | orchestrator adapter only (it is the parent of every worker) |
| `src/mcp/belay-mcp.cjs` | the binary: `node belay-mcp.cjs --role orchestrator\|worker --run <id> [--data <dir>] [--worker-id <id>] [--no-embed] [--log <file>]`; `--data` defaults to `<cwd>/.belay`; `--log` may not point inside the data dir except under `workers/<worker-id>/` where the id is the caller's own, so an orchestrator adapter never logs inside the data dir | one process per orchestrator session, one per worker |

- `openCore({ dataDir, caller, embed = true })`. `caller = { role: 'orchestrator'|'worker'|'operator', worker_id?: string, run_id: string, pid: number }` comes from argv and never changes for the life of the process. `openCore` opens no file, takes no lock, and requires no embedding library. The owner loads the embedder on the first call that needs a vector (ADR 0012); every non-vector method works with no model present.
- Every Core method is `async`, takes one plain object, and either resolves to exactly the row shape listed below or rejects with `CoreError { code, message, detail? }`. Never both. Never a bare status word.
- Mode is chosen per call by the core, not the caller. Reads ask a live owner first with a bounded round-trip (connect, write, read, 300 ms timeout; 100,000 ms for a `memory.search` of mode `semantic` or `hybrid` that the owner must embed, or a `memory.store` without `embed: false`, since the copy fallback has no embedder; a `keyword` search or one that supplies `query_embedding` takes the ordinary 300 ms bound and may fall back to the copy, and a `hybrid` search whose owner is wedged or still loading falls back to the copy and reports the cause in `modes_failed`, see "Bounds and liveness for a vector call" in §3) and fall back to copy-then-read: copy `memory.db` and its `-wal`/`-shm` into the OS temp dir, read the copy, delete it. The copy lives at `<tmp>/belay-ro/<pid>-<random>`; a read removes its own copy before it resolves. `<tmp>/belay-ro/` itself is the one persistent empty directory a read leaves behind: belay's scratch parent in the temp dir, never in the data dir, created with mkdir -p semantics and never removed by reads (removing it raced concurrent readers). Before copying, a read also removes at most 20 copies left by readers killed mid-read: those whose pid is dead and whose directory is older than 60 s (a live or reused pid keeps its directory). That is cleanup of belay's own scratch in the temp dir, never of the data dir, and it creates no file. Old `belay-ro-XXXXXX` directories directly in the temp dir are not touched. Never a read-only open of the live file, never `immutable=1`. Writes connect to the owner or, if none answers, win `owner.lock` (published whole by a rename that fails while any lock is there; a stale lock is taken over in place by exactly one claimant, `src/core/lock.cjs`) and become the owner in-process for the caller's lifetime (pipe server included). A worker-role caller never elects; it fails `E_NO_OWNER`.
- `core.readBatch(fn)` runs `fn()` so that every read it makes is served from ONE source, chosen by the first read: the owner if it answers, otherwise one copy of the store (taken at that read, deleted when `fn` settles). A batch on the copy never asks the owner again, so a later read cannot show a newer row than an earlier one; a batch on the owner whose owner stops answering fails `E_OWNER_LOST` and does not fall back to a copy. Each read reports its own `note` and `embedderFailure`: a read after the first on the copy carries the reason the batch is on the copy, which is true of all of them. Reads only; a write is not part of the batch. `belay notices` uses it, so it makes one copy instead of one per core call.
- `core.close()` disconnects. `core.shutdownOwner()` is the only way to stop an owner: in-process `stop()` or the pipe `shutdown` method. Never a signal. `core.isOwner()` and `core.ownerInfo()` are sync.
- `core.becomeOwner()` (build step 5a-2, refusal wording fixed by 5a-3, refusal `pid` fixed by the 5a-3 fix round, refusal `established_by` wording fixed by 5a-4) elects explicitly, before any other write: it resolves `{ owner: bool, pid, established_by }`. `established_by` is `'won the lock'` when this process now holds it, `pid` its own. On refusal it makes one bounded ping over the lock holder's pipe (300 ms, invariant 7) and reports one of two shapes only: `'a bounded ping answered in <ms> ms'` when it did, or `'a ping to the lock holder's pipe failed: <code>'` naming whatever code `ping()` itself returned (`E_TIMEOUT`, `E_OWNER_LOST`, `E_NO_OWNER`, or the socket's own error code) when it did not — never a sentence that claims a connection the ping did not make. `pid` is the pid the ping itself answered with when it answered (a fact this call just established), and only when it did not falls back to a retried read of the lock file, which can be `pid: null` if even that never resolves. A worker-role caller gets `E_ROLE`.
- **Binds (ADR 0045 decisions 2 and 3, built; amendment 1).** Three more owner verbs, the owner's own and never the engine's: `bind.open { identity: { role: 'orchestrator'|'worker', run_id, worker_id? (worker only), }, no_expiry? }` -> `{ bind_id, pipe, caller, expires_in_ms }` (`expires_in_ms` null with `no_expiry: true`, which only the operator may ask for), `bind.status { bind_id }` -> `{ bind_id, state: 'open'|'claimed'|'revoked'|'expired', claimed, caller, opened_by }`, and `bind.revoke { bind_id }` -> `{ bind_id, was, state, caller }`. The operator (the run process, or an owner's own in-process call) may bind an orchestrator or a worker; an orchestrator only a worker of its own run (`E_ROLE` otherwise); every other role `E_ROLE`; another run's bind `E_ROLE`, an unknown id `E_NOT_FOUND`. The bind's `pipe` is a one-shot pipe: one connection is handed `{ bind_id, key, caller }` (a fresh 256-bit key) and the listener closes. `Core` exposes `bindOpen(identity, { noExpiry? })`, `bindStatus(id)` and `bindRevoke(id)`. **The `key` field on the wire:** a request line may carry `key` beside `id`, `method` and `params`; the owner then takes the caller from the bind the key names and ignores the request's own `caller` (except a `pid`, and a request for the `tool` channel; the `harness` channel only on an orchestrator bind). A `Core` built with `key` sends it on every request and never elects. **Owner `mode`:** `'claimed'` (the default) believes an unkeyed request's caller, as ADR 0012 decision 3 does; `'bound'` serves an unkeyed request only as `anonymous` (reads open to every role) and refuses its writes `E_UNBOUND`, unless `opts.operatorCheck({ conn, caller, method })` returns `{ ok: true }` for a claimed operator (no check: fail closed). `belay run` serves `bound` where the operator check exists (Windows; amendment 2): the owner also listens on `127.0.0.1` and publishes `tcp_port` and `mode` in `owner.lock`; a keyless operator dials that port, and the owner accepts it only after reading the peer's pid from the connection table and following its ancestor chain (`src/core/operator-check.cjs`): a descendant of a worker or of the headless orchestrator, an orphan, or a pipe client is refused `E_UNBOUND` (`reason: operator_check`); "a process belay spawned" is read from the machine-wide spawn register (`src/core/spawn-register.cjs`), so another store's workers count, and an unreadable register refuses. An open read from an unverified caller is served `anonymous` at once with no check; the client asks for the check only before a call that needs the operator (ADR 0045 amendment 3). A launch that fails at any point up to its `running` row revokes its bind and ends its child, and `E_NO_READY` carries `bind_id` and `bind_revoked`. The adapter takes `--bind <pipe>` and claims it before it answers `initialize`; the identity returned must equal its argv's `role`, `run` and `worker-id`, or it exits 3.
- Pipe: `\\.\pipe\belay-<sha1(lower(resolve(dataDir)))[:12]>` on Windows, `<dataDir>/belay.sock` elsewhere. NDJSON, request `{ id, method, params }` with `params.caller` set by the client from its own argv, response `{ id, result }` or `{ id, error: { code, message, detail } }`. Method names are the dotted names below, plus five pipe-level methods: `ping` (any caller), `shutdown` (orchestrator or operator only, `E_ROLE` otherwise), and the three run controls `run.stop`, `run.pause` and `run.resume` (build step 5c for `run.stop`, build step 6f for `run.pause`/`run.resume`, ADR 0023 amendment 3 decision 4; operator only, `E_ROLE` otherwise; each dispatched to a control this owner was constructed with — `new Owner(dataDir, { controls: { 'run.stop': async (params) => ..., 'run.pause': ..., 'run.resume': ... } })` (`Owner._dispatchRunControl`) — never to the engine; an owner built with none of the three registered answers `E_NOT_FOUND` naming the method and that it is not a belay run process, `detail.controls` the (empty) list of what it does register). The prototype's `embedding_b64` wire encoding is kept. `owner.lock/owner.json` carries `pid`, `pipe` and `listening`; it is written with `listening: false` at election, and once `listen` succeeds the owner publishes `owner.lock/listening-<token>.json` (a new file, so readers polling `owner.json` cannot block it) and then rewrites `owner.json` with `listening: true`, best effort. `readOwnerLock` reads a lock as listening when either says so for that lock's token; a client that finds it not listening does not dial. An owner that cannot publish the marker fails its start with `E_INTERNAL` and releases the lock, so no owner holds the lock undialable. Build step 6d: one method kind is neither read nor write — `permission.wait` (kind `wait`) is served only by the live owner's own engine through its in-process waiters, dispatched through the write path (`_write`, so a worker with no owner lands `E_NO_OWNER` having created nothing, and a copy is never asked to wait), with a deadline of `params.timeout_ms + 5000`.
- **The worker adapter's own pipe** (build step 6c, ADR 0019 decisions 2-5 and amendment 1, extended by build step 6e, ADR 0023 decision 4, rebuilt on the park design by 6e-4, amendment 2): a second pipe, `\\.\pipe\belay-<hash>-<adapter_pid>` on Windows, `<dataDir>/belay-<hash>-<adapter_pid>.sock` elsewhere (`src/core/lock.cjs` `adapterPipeName(dataDir, pid)`, pure, never stored), opened by the worker adapter (`src/mcp/belay-mcp.cjs` in role orchestrator) the moment it creates its `RunManager` and closed with it — never while the manager is only idle, its idle cost measured and recorded ungated. It serves exactly five methods, operator only (`E_ROLE` otherwise): `worker.message`, `worker.stop`, `worker.restart`, `worker.pause`, `worker.resume`, each a direct call of the `RunManager` method of the same name with `caller` stripped (for `pause` and `resume`, `by` is set from `caller` instead — `${caller.role}:${caller.pid}`, overwriting any `by` the arguments carried, so the caller names itself on the pipe and never in its own arguments), answering with that method's own receipt or error verbatim; any other method is `E_NOT_FOUND` naming the five. The CLI reaches it through the run row's `adapter_pid` (`src/cli/adapter-pipe.cjs`'s five-rung ladder: the worker row, the run row, a pid check on `adapter_pid`, the connect, then the bounded call), never elects, never dials with nothing to dial. Build step 6e-4 (ADR 0023 amendment 2 decision 3): `pause`, `resume`, `restart` and `stop` share one per-worker operation slot (`src/run/lifecycle.cjs`) instead of three separate in-flight promises — the same operation already in flight is shared (one receipt), a different one is refused `E_BUSY` naming it, except `stop`, which waits out whatever is in flight and is never refused. **Tickets (ADR 0045 decision 5, amendment 4, proposed):** each of the five requests carries `params.ticket`, which the adapter redeems with the owner before it calls the manager; a missing, used, expired or mismatched one is `E_ROLE` with `detail.reason: 'ticket'` and the manager is not called. Two more owner verbs, beside `bind.*`: `ticket.issue { run_id, worker_id, verb }` (operator only; on a bound owner a keyless claim takes the operator check) -> `{ ticket, run_id, worker_id, verb, expires_in_ms }`, and `ticket.redeem { ticket, worker_id, verb }` (orchestrator only, a ticket of its own run) -> `{ redeemed: true, run_id, worker_id, verb, issued_to, age_ms }`. `verb` is `message|stop|restart|pause|resume`; a ticket is single use (consumed by its first redeem) and lives 30 s in the owner's memory only. `Core` exposes `ticketIssue(args)` and `ticketRedeem(args)`; `ticketIssue` from a process that is not the owner goes through `control` and never elects (`E_NO_OWNER` naming the missing fact when no owner is live). The ladder asks for the ticket after its pid check and names it on that rung (`ticket`).
- `core.control(method, params, { timeoutMs = 60000 })` (build step 5c, the lock-present case fixed in 5c-2) is mode C: it never elects and never dials with nothing to dial. It reads `owner.lock` first and rejects `E_NO_OWNER` on five causes, naming which: no `owner.lock` directory exists at all; the directory exists but `owner.json` names no readable owner yet even after riding out the write window `rereadOwnerPid` rides for `becomeOwner()` (`an election may be in progress`, `detail.lock_dir_present: true`) — neither of those two touches the network; its pid is dead; it says `listening: false`; or, once those checks pass, the connect itself fails, naming the connect error. Otherwise a short-lived client (`elect: false`) carries this caller's identity across exactly as `shutdownOwner()`'s remote path does, calls `method` with a `timeoutMs` deadline (default 60,000 ms), and is closed in a `finally`. The result is returned as the owner answered it; a `CoreError` the owner returned (an `E_ROLE` or `E_NOT_FOUND` from `run.stop`'s own gate, say) is rethrown as is.
- Data dir layout, nothing else: `memory.db` (+ sidecars), `owner.lock/owner.json`, `workers/<worker-id>/{mcp.json, settings.json, argv.json, stream.jsonl, stderr.txt, adapter.log, resume.md, sent.jsonl, corpus.md}`, `scratch/<run-id>/<worker-id>/` (a reviewer's probes only, ADR 0054 amendment 1: outside every worktree and holding no worker transcript or store file, deleted at that run's close), `tmp/`. `sent.jsonl` (ADR 0042, only with `memory.bottle` on) is the record of every message the run manager wrote to that worker's stdin, one JSON line `{ seq, turn, kind: 'task'\|'message'\|'wake'\|'resume', text }`, append-only, with `text` redacted before it is written and `turn` the 1-based turn the message starts or is folded into (one more than the number of `result` lines the stream holds when it is written); the stream holds no user text, so the bottle reads this. `resume.md` is the store-derived resume document of ADR 0007, or, on the replace branch with `memory.bottle` on, the bottle: the worker's own assistant text verbatim, one line per tool call, and the sent messages, redacted, written whole through a temp file and a rename, never appended. `corpus.md` exists only under the knowledge agent's directory `workers/knowledge-<run id>/` (ADR 0043, `memory.knowledge_agent` on): `memory.corpus`'s text, rewritten atomically when its sha256 changes. Build step 4c: `stream.jsonl` is a fact of this layout, not of the store, so `worker.get` states its path (`stream_path`, forward slashes) and size (`stream_bytes`, or `null` when the file does not exist yet) rather than a caller deriving it — the CLI must not import `src/run`, and the layout is stated once, here.
- Times are epoch milliseconds. Ids are UUID v4 strings unless stated. JSON columns are text in SQLite and parsed objects on the wire. Every row carries `seq`.
- Rows supersede, never mutate. Every new table is append-only with `seq INTEGER PRIMARY KEY AUTOINCREMENT` and `written_at`, `written_by` (the caller's `worker_id` or role). The current row of an id is its highest `seq`. No `UPDATE` is issued against these tables.

## 2. Tables (new; `memory_entries`, `namespace_models`, `owner_heartbeat`, `meta` are lifted, `memory_entries` with the additive columns and keyword index below)

**Schema stamp (memory plan G3, `src/core/schema-stamp.cjs`).** `meta.schema_version` (integer text, `SCHEMA_VERSION` = 2; bumped by hand only for a layout an older core cannot read or would write into wrongly, never for an additive column alone; version 2 is the memory columns with redaction, ADR 0040 §1, which a version-1 core would fill with unredacted rows that read as scanned-clean) and `meta.written_by` (`belay@<package version>+<12-char commit>`, `unknown` when no checkout and no `gitHead`). Both are written by the owner's open for write only (`new Store(path, { stamp: true })`, from `Owner.start`), in the same `BEGIN IMMEDIATE` as the version check and `ensureSchema`, so a migration that does not commit leaves the old stamp: `written_by` names the build that last opened the store for write, `schema_version` is set to this core's. A store with no stamp predates G3 and counts as schema 1. The commit is read from `.git` files (worktree `gitdir:` and `commondir` followed, loose ref then `packed-refs`), never by spawning git, once per owner start. Reads never stamp: they open a copy, and the version check runs on that copy before `ensureSchema`, so a newer store is refused with `E_SCHEMA_NEWER` and the live store is untouched. `status.get` reports the stamp (§4 `store`); the commit is not marked dirty, because a dirty check needs the index and the working tree compared, which `.git` files alone cannot do reliably or cheaply.

- `worker.state` ∈ `starting | running | idle | paused | stopping | stopped | dead | forgotten`. `idle` is Codex between turns (its process exits by design; the thread lives). `running` requires a live pid at the moment it is written. `paused` (build step 6e-4, ADR 0023 amendment 2 decision 5) is **not** a live state: a park ends the worker's process, so a `paused` row needs no live pid, only `paused_by` a non-empty string and `paused_at` an integer; it carries `session_id` so a resume can relaunch on it. Every row not `paused` carries `paused_at`/`paused_by` both `null`. `forgotten` (build step 6b) is written only by `worker.forget`; `worker.write` refuses it as an argument (`E_ARGS`).
- `task.state` ∈ `open | assigned | released | done | cancelled`. `done` is written only by `task.evaluate` when every executable check passed; `cancelled` only by `task.cancel` (ADR 0058). Both are final: `task.assign` and `task.evaluate` refuse them, and a cancelled task holds none of its `files_owned`.
- `task.acceptance = { commands?: [{ argv: string[], cwd?: string, timeout_ms?: number }], files_within_owned?: boolean }`. `files_owned` is a string array of paths relative to the worktree.
- `task.results = { evaluated_at, executable: bool, passed: bool, checks: [{ kind: 'command'|'files_within_owned', argv?, exit_code?, ms, passed, detail }] } | null`.
- `task.depends_on` is a string array of task ids, or null (ADR 0013 §1). Written once, by `task.create`; no method changes it. Every id must already have a row, so the graph is acyclic by construction and `task.create` refuses a cycle anyway. A dependency is cleared only by reaching `done`, which only `task.evaluate` writes.
- Lease rows: `task.assign` inserts a new lease id with `supersedes` = the previous lease id; `lease.renew` inserts a row with the same id and a later `expires_at`; `lease.release` inserts a row with the same id and `released_at` set. The current lease of a task is the highest-`seq` lease row for that task; no holder if `released_at` is set. Default TTL 600,000 ms; renew extends to now + TTL. ADR 0026 amendment 1 (proposed): a worker's first `dead` row (written by `worker.write`, `run.attach` or `run.end`) releases, in the same transaction, every current unreleased worker lease it holds, expired or not: a released row with `released_reason` `holder_dead` (null on every other release), and its task, if `assigned`, goes back to `open` (its files stay held by the task). The dead row's `leases_released` names them, `[{ lease_id, task_id }]`, null when it released nothing; a later `dead` row of the same death keeps it, and any other row has it null. A `paused`, `stopped` or later `dead` row releases nothing.
- `checkpoint.source` ∈ `worker | harness`. `stated = { summary, next_step, open_questions[] }` is only ever what a worker said. `tool_digest = [{ tool, args_sha256_12, result_bytes, at }]` (last 20) is only ever derived from the stream by the run manager. Every consumer labels which is which.
- `worker.mid_turn` (build step 5b) is a harness-derived claim, never a worker's: 1 on a `starting` or `running` row written while the harness has put a message on that worker's stdin (or launched a Codex process with a prompt) and no `result` has landed on its stream since; 0 on every other row `worker.cjs`'s `rowOf` writes. A row written before this migration landed, or planted directly through the store rather than through the run manager, carries `NULL` rather than a claim either way. `worker.death_established_by` carries, on a `stopped` or `dead` row, the string the death detector recorded (`exit-event`, `pid-poll`, `spawn-error`, an `a+b` combined form, or `'adopted from the store, not seen exit by this adapter'`); null on every other row.
- `worker.permission_mode_requested`, `worker.permission_mode_effective` and `worker.claude_code_version` (ADR 0021 decisions 3 and 4) are the harness's reading of a Claude Code launch's own `system/init`: the mode the launch asked for, the `permissionMode` the session reports it started in, and `claude_code_version`. Written from the ready gate on, carried by every later row of that launch, and null on a Codex row, on a row written before the ready event, and on an adopted record that has not relaunched. A mismatch is not refused: `auto` falls back to `default` on a model without auto mode (Haiku), which is stricter, and `spawn` and `restart` say so with `permission_mode_degraded: true`; `belay run`'s `orchestrator` block carries all four for the orchestrator.
- `worker.paused_at` and `worker.paused_by` name when and by whom (`<role>:<pid>`, as `verdict_by` in ADR 0020) a `paused` row was written; both `null` on every row that is not itself `paused`, so the merge (above) cannot inherit a stale pause — including the rows `run.attach`, `run.end` (ADR 0029) and `worker.forget` append directly (not through `worker.write`'s own merge), which both clear both fields the same way.
- `worker.park_turns` (build step 6i design item 1) is the harness's own claim, not `worker.write`'s to set: the worker's `turns` at a park's own acceptance (`pause.cjs`'s step 1b `stopping` write), carried by every later row of that same park (`worker.cjs`'s `rowOf`) and reset to `null` by the next `starting` or `running` row. `null` on a `stopping` row from a plain stop (never parked) and on every row `worker.cjs` never wrote.
- `worker.pid_created`, `worker.pid_created_error`, `worker.pid_image` and `run.adapter_pid_created` (ADR 0039 decision 1; additive, nullable) are the harness's own claim, never `worker.write`'s caller's. `pid_created` is the creation time in epoch ms of the process the row's pid names, read once at spawn from one CIM snapshot (`src/core/process.cjs` `createdOf`); `pid_image` is the executable image the spawner launched (the basename of the child's spawnfile). `pid_created` is null on a row written before the column and on a row whose read failed (including a child that had already exited when it was read), in which case `pid_created_error` says why. The first rows of a launch go out before the read finishes; a restating row carries it when it lands. A kill (`killPid`, `killTree`, `killProcess`) takes a live child handle, or `{ pid, created, image }` from the row (`rowTarget`), and proves the target before signalling:
  - a live handle is its own proof (`identity: { via: 'handle' }`); a bare pid number is refused;
  - `{ pid, created }` must match one snapshot taken for that kill EXACTLY (two snapshots of one process agree to the millisecond), and its image must match too, case-insensitively with an extensionless name read as `.exe` on Windows (`identity: { via: 'created', created, image }`);
  - a null `pid_created` is never tree-killed; at most the root gets a single-pid kill when the snapshot image is the row's `pid_image` (`via: 'image'`), and the result says `descendants_not_killed`; a row with `pid_created_error` is refused outright;
  - a refusal is `{ ok: false, refused: 'identity', kind, detail }`. `kind` is `mismatch` (the creation time differs) or `absent` (the pid is not running), both of which prove the worker is not at that pid, or `unverifiable` (an image difference at a matching creation time, an unreadable snapshot, no recorded time), which proves nothing and so never allows a terminal row for a pid that is still alive;
  - the snapshot is taken for the kill; a fast close (a console closing) may reuse one that completed under 250 ms before, or one still in flight, and otherwise refuses and records `kind: unverifiable` when the budget cannot pay for a fresh one.
  Read verbs never take a snapshot.
- Per-agent receipts (build step W2-3). Set by the worker adapter from the substrate's own stream and the worktree, never from anything a model said (invariant 3), and carried by the merge like every other column:
  - `model` is the model the session's `system/init` reported it started with, not the string that was requested. `null` on the `starting` row and for Codex, whose stream names none.
  - `input_tokens`, `cache_read_tokens` and `cache_creation_tokens` mean the same on both substrates: input_tokens is UNCACHED input only. Claude Code reports them separately (`usage.input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`) and they are summed per turn. Codex reports `input_tokens` as a total with `cached_input_tokens` a subset, so the adapter stores `input - cached_input` in `input_tokens` and `cached_input` in `cache_read_tokens`; `cache_creation_tokens` stays 0 for Codex. `output_tokens` is summed per turn.
  - `cost_usd` is SET from the latest cumulative `total_cost_usd`, never summed (it carries across a `--resume`); Codex reports none and stays 0.
  - `tool_calls` is an uncapped count of every `tool_use` the parser reported, over the worker's whole life including across restarts and adoption. The checkpoint's `tool_digest` still keeps only the last 20.
  - `base_sha` is `git rev-parse HEAD` of the worker's worktree, captured asynchronously when the adapter creates the worker record and written with the next row write (it never blocks the spawn). `head_sha` is the same command run when the worker settles, but the terminal row (dead, stopped, paused, idle) is written first, exactly as without receipts; when git answers, a FOLLOW-UP row of the same state restates it with `head_sha` set (the way the exit-code fill-in writes a second row). A reader wanting the head therefore reads the latest row, and may see one terminal row without it for tens of milliseconds. The lookup is retried, up to 3 attempts with 150 and 300 ms backoff, all inside 5,000 ms (the old single attempt's own bound; the shutdown drain waits 5.5 s, so a git killed at its timeout still lands its `head_error`); an attempt gets all the time left, and only a spawn failure (`EAGAIN`, `EMFILE` and the like) is retried, never a timeout or a git that ran and failed. A lookup that fails every attempt writes the same follow-up row with `head_sha: null` and `head_error` naming why (`git rev-parse HEAD timed out after 5000 ms`, `not in a git repository` and so on), so a missing head is visible; `head_error` is `null` on every row that has a head and on live rows. A `base_sha` that answers after the last row was built is restated in one guarded follow-up row of the current state. `base_error` mirrors `head_error` for the base: null on every row that has a `base_sha`, the lookup's reason when every attempt failed, restated like a late `base_sha` except for a worktree in no repository. A live (`starting`/`running`) row carries `head_sha: null`. Both shas are `null` when git cannot answer (a directory in no repository, no git, every attempt timed out; then `head_error` says which for the head, and `base_error` for the base). An adopted worker keeps `base_sha` from its row and asks git for `head_sha` if it later settles.
  - The turn-level counts of a turn that never ended (a worker killed mid-turn) are not in the row; the worker's `workers/<id>/stream.jsonl` remains the full record.
- `run.orch_*` (build step W2-3) is the orchestrator's own receipt, written once by `belay run` at `run.end` from its accumulator: `orch_model` is the model `system/init` reported (not the requested string); `orch_input_tokens` (uncached), `orch_output_tokens`, `orch_cache_read_tokens` and `orch_cache_creation_tokens` are summed over the orchestrator's turns; `orch_cost_usd` is the latest cumulative `total_cost_usd` (set, not summed); `orch_turns` counts its `turn_end` events.
- `run.orch_effort_requested` (build step S6b, ADR 0028 decision 5): the level `belay run --effort <level>` passed to this epoch's orchestrator launch, `null` when not asked. It is never carried from an ended epoch of the same run id. A level outside `low | medium | high | xhigh | max` is a usage error, exit 2. The `belay run --json` receipt names it as top-level `orch_effort_requested`.
- `worker.effort_requested` (build step S6b, ADR 0028 decision 3): the level the spawn asked for, `null` when not asked. It records the request, not the level the substrate used (`system/init` carries no effort field). Inherited across restating writes.
- `worker.max_budget_usd`, `worker.model_requested` (ADR 0024 amendment 4, proposed): the cost cap and the model the spawn asked for, `null` when not asked and on a row written before the columns. Beside `tools`, they are the harness's record a relaunch in another process reads, never the worker's argv.json. `model_requested` is the request; `model` is what `system/init` reported.
- `task.handoff` (build step W2-1, ADR 0025): Shape `{ result, by, lease_id, at, memory_ids_missing? }` (`memory_ids_missing` only when `result` carries a `memory_ids` key, ADR 0040 decision 6): `result` is the object a worker passed to `lease.release`, `by` the releasing worker's id (from argv), `lease_id` the lease it released, `at` the release time. Written only by a `lease.release` that carries a `result`; every other writer of a task row (`task.assign`, `task.evaluate`, `lease.takeControl`, a release without `result`) carries it forward unchanged. It is a worker's claim, like a checkpoint, until the orchestrator's `task.evaluate` uses it as verdict evidence.
- `lease.ttl_ms` (ADR 0025 amendment 1): the lease's own length in ms, written by `task.assign`, `lease.takeControl` and `lease.renew` (the `ttl_ms` argument or the 600000 default) and carried forward by `lease.release`. `expires_at - granted_at` is not the length after a renew, because renew leaves `granted_at`; `ttl_ms` is. Rows written before the column read `null`. The `lease` object in a task view (`task.list`, `task.get`) carries `id, holder, holder_role, granted_at, ttl_ms, expires_at, expired`.
- `permission.state` ∈ `pending | allowed | denied | expired` (build step 6d, ADR 0020 decision 2). `id` is the substrate's `tool_use_id`, unique per call; the request row and the verdict row share it, and the current row of an id is its highest `seq`. `verdict_by` is `<role>:<pid>` for an operator or orchestrator's allow or deny, and `adapter-bound:<pid>` for the adapter's own expire. `input` stays a string on the wire, never parsed: a truncated JSON text (`input_truncated: 1`, cut at 8,192 bytes) does not parse as JSON at all, and the operator reading `pending` needs to see the digest as text either way.

- **Memory row columns (ADR 0040).** All new `memory_entries` columns are nullable and `SCHEMA_VERSION` is 2 (a version-1 core refuses the store, `E_SCHEMA_NEWER`, rather than write unredacted rows into it); a row written before them reads as untitled, `unverified` and of unknown source. `title` is at most 160 bytes, one line; a read derives it from the first non-empty line of `text` when it is null and never writes it back. `status` ∈ `unverified | verified | refuted` (null reads `unverified`), with `status_receipt`, `status_by` (`<role>:<pid>` or the worker id) and `status_at` as its evidence; only `memory.setStatus` writes them. `run_id`, `task_id` and `turn` are derived provenance (below, `memory.store`), never self-reported. `source` ∈ `model | harness | operator | summariser | import`. `redactions` is JSON `{ kind: count }`, null when nothing was redacted, `{"disabled":1}` when the run's `memory.redact` lever was off. `body` is a JSON object of at most 8,192 bytes for a structured row (an observation or a summary), parsed on the wire. Indexes: `ix_entries_run`, `ix_entries_task`, `ix_entries_status`, `ix_entries_ns_created`.
- **`written_by` (ADR 0044 decision 6).** Who wrote the row: `worker:<id>`, `orchestrator` (the orchestrator model, through a tool), `harness` (belay itself: the run manager's turn, observation, summary and project-copy rows, and the run-end jobs) or `operator` (the CLI). Nullable; a row written before the column, or by an older core, reads `null` (shown as `unknown` where a view labels it) and nothing guesses it. The core sets it on insert from the caller and never changes it, a dedup update included; `memory.store` refuses it from any caller (`E_ARGS`, as every core-set field), and a `caller` inside a call's arguments is replaced by the process's own. The harness channel is a frozen caller identical to the process's own except `channel: 'harness'`, handed only to the run manager (`Core.harness()`, used by `src/mcp/belay-mcp.cjs` and `src/cli/run-memory-end.cjs`); the MCP tool router uses the plain caller. An orchestrator or operator caller may carry `channel: 'harness'`; a worker's is `E_ARGS`. `written_by` cannot be set through the MCP tools. But the pipe trusts the caller a client sends exactly as it trusts its role (ADR 0012 §3), so a process with direct access to the owner's pipe (a worker's Bash, for one) can claim any caller, the harness channel included; the exposure is the same one `role` has. It appears in the full and index views, `memory.list` and a diff row. A `memory_verify` project copy is written `orchestrator` (`harness` when the harness channel makes the call). An imported row (`belay memory import`, `source: import`) reads `written_by: operator`; the original writer is not carried. `memory_event` rows written on the harness channel (the run manager's) carry `written_by: harness` in that table's own `written_by` column; `usage` rows keep the role. `last_writer_id` is **legacy**: the worker id the last write named (for a harness row about worker `w1` that is `w1`), kept so an older core writing into the same store keeps its meaning; attribution reads `written_by`.
- **The keyword index.** `memory_fts` is an external-content FTS5 table over `memory_entries(title, text)`, `tokenize='trigram'`, kept in step by three triggers (after insert, after delete, after update of `title` or `text`; a status change does not fire them). It is created, with its triggers and backfill, by the owner's open for write only (`src/core/memory-schema.cjs`, one `BEGIN IMMEDIATE`), after `sqlite_compileoption_used('ENABLE_FTS5')` says it can. `ensureSchema`, which also runs on every read copy, never creates it. `meta.memory_fts_version` is `'1'` when the index exists, `'0'` when this SQLite lacks FTS5 (no index is built), and absent when no owner has opened the store since the index landed; `memory.stats` and `belay doctor` report it. An older core's writes keep the index current through the triggers.
- **`memory_event` (ADR 0041 decision 3).** One receipt for each harness memory action, append-only. `kind` ∈ `observation | summary | project_write | usage | index_injected | bottle | wrapup | corpus_primed | knowledge_ask` (and, from the notes lifecycle, `notes_applied`, `note_chance` and `note_changed`: see `memory.recordChances`; `note_matches`: see `memory.embedNote`; `note_review`, `note_brief`, `note_refuted` and `review_job` (written only when applying a review task's verdicts fails, key `route:<task>`; the note-review job is removed): the note review (`note_brief` fixes the notes a brief listed); `scrub_job`, `scrub_owed`, `scrub_alarm`, `review_stage` and `stage_overrun`: the run-close stages; `archive_purge`: `memory.archivePurge`). `ok` is 1 or 0; a failed action is recorded `ok: 0` with the `code` that failed it, never skipped. `key` is `task:<id>` or `run` for a `wrapup` (a failed run-end attempt records `run:gave-up`), `copy-of:<source id>` for a `project_write`. `row_ids` is a JSON array of the memory row ids the action touched or showed, `sha256` and `bytes` describe the text it produced, and `dropped` and `over_budget` say whether a bounded block lost whole items or could not fit even its frame. A partial unique index `ux_memory_event_wrapup` on `(run_id, key) WHERE kind = 'wrapup' AND ok = 1` makes a second successful wrap-up for one key fail at the store (`E_EXISTS`); a failed wrap-up (`ok = 0`) is a receipt, not a claim, and does not block a retry. A store made before the index counted `ok = 0` rows is upgraded by the owner's open for write. A partial index `ix_memory_event_promote` on `(key) WHERE kind = 'project_write' AND ok = 1` serves the index's promoted-row lookup; the owner's open for write adds it.
- **`usage` (ADR 0041 decision 6).** One row per turn when the run's `memory.cost_ledger` lever is on. `cost_basis` ∈ `delta-of-cumulative` (Claude Code: `total_cost_usd` is cumulative per process, so the row carries the difference from the previous turn of the same process), `delta-of-cumulative (new process)` (the first row after a relaunch, whose delta restarts from zero), or `none` (Codex reports no dollars). `none` requires `cost_usd` null and every other basis a non-null `cost_usd`.
- **`run.memory_levers` and `run.project` (ADR 0041 decision 1).** `memory_levers` is the parsed `memory` block of the run spec as JSON text (every key present, defaults filled), `project` its project name. Both are written by `run.attach`, carried forward like `max_fix_rounds` only while the previous epoch has not ended, and null for a run with no `memory` block or an all-default one.

**Embedding (build step E1, ADR 0027).**
- **Model.** The default is `onnx-community/voyage-4-nano-ONNX` at a pinned commit, q4, mean pooling, its native 2048 dims truncated to 1024 and L2-renormalised, `max_tokens` 8192; `src/core/models.cjs` is the table (a MiniLM entry is kept). Without `embedding`, `memory.store` embeds `text` as a document; without `query_embedding`, `memory.search` embeds `query` as a query; each prepends the model's prompt for that case. A text whose token count, prompt included, exceeds `max_tokens` is `E_TOO_LONG { tokens, max }`.
- **Which model a store uses**, in this order and no other: `meta.embedding_model`; else, when any row carries an embedding, those rows' model (`namespace_models`); else the owner's `embedOpts.model`; else the default. It fails closed: a store with no identity and rows under a model the table does not know, or rows of more than one model, is `E_MODEL_CHANGED` (`detail.needs: 're-embed'`) for every text store and search; caller-supplied vectors still store and search.
- **Identity in `meta`**: `embedding_model`, `embedding_sha`, `embedding_dtype`, `embedding_pooling`, `embedding_dim`, `embedding_library`, `canary_vector` (JSON array) and `canary_sha256` (legacy, never compared), all written in one `BEGIN IMMEDIATE` on the first load against a store or on adoption. Only the exact legacy MiniLM shape (`canary_sha256`, `embedding_model = Xenova/all-MiniLM-L6-v2`, `embedding_dim = 384`, no `canary_vector`) adopts; any other partial identity is `E_MODEL_CHANGED` with `detail.reason: 'incomplete identity'`. At load the canary (a document) is compared by cosine: at or above 0.9999 passes, below is `E_MODEL_CHANGED` naming the cosine; a different id, sha or dims is `E_MODEL_CHANGED` without loading. A passing canary under a changed library is logged once and recorded. The outcome of a load, good or bad, is sticky for the owner's life, and every failure carries a code (`E_INTERNAL` when the cause had none).
- **The embedder process.** The owner forks a child (IPC, `execArgv: []`, an allow-listed environment: `PATH`, `SystemRoot`, `TEMP`, `TMP`, `LOCALAPPDATA`, `APPDATA`, `USERPROFILE`, `HOME`, `XDG_CACHE_HOME`, `BELAY_MODEL_CACHE`, `BELAY_TRANSFORMERS_PKG`, and `BELAY_TEST_MODE` when set) and knows it by pid. `embed` and `tokenCount` are bounded at 60 s each, and an op that times out marks the embedder failed (cause `timeout`, phase `op`): later ops fail at once with the same error and `memory.warm({ reload: true })` closes the hung child by its exact pid and loads afresh; `load` is not bounded by a fixed 90 s any more (build 12b E2): it is waited on, and its only bound is a 10 min backstop for a hung child (`E_EMBEDDER_TIMEOUT`, `cause: 'timeout'`), while a child that dies rejects at once. The caller's own limit (below) ends the CALL, never the load: the owner keeps one load promise, so a later call waits on the same load and nothing restarts it. A load that failed is reported with its cause to the call that met it and, sticky for the life of that owner (cleared only by `memory.warm({ reload: true })` or an owner restart), promptly to every later call with the same code and cause. On owner stop: `close`, at most 2,000 ms grace, then a kill by exact pid. When the owner dies the IPC channel closes and the child ends by itself. A child that dies after a good load makes later vector calls `E_MODEL_ABSENT` naming its pid and exit code; it is not restarted within that owner. **Call limit in the owner's own process (review 1, S2):** a vector call made by the process that holds the lock (`belay memory store`, a re-elected adapter, `belay run`) has the same 100,000 ms limit a pipe client has, ending the call with `E_TIMEOUT { in_process: true }` while the load continues; there is no exception per caller. **Fork stall:** the embedder child is forked on the owner's loop, stalling it 80-365 ms. An owner that has not been warmed (a CLI-elected owner, for instance) still pays it at its first vector call; the 2,000 ms re-ping covers it, and `memory.warm` moves it ahead of any caller. **Embedder failure signature (build 12b E2), the canonical list:** every embedder failure carries `detail.embedder === true` and `detail.cause`, one of `absent | dead | timeout | load_failed | op_failed | canary`: `E_MODEL_ABSENT` (`absent` package or model; `dead` child exited, unreachable or closed, with `pid`, `exit_code`, `signal`), `E_MODEL_CHANGED` raised while loading (`canary`: the store's identity or canary does not match), `E_EMBEDDER_TIMEOUT` (`timeout`, `phase` `load` or `op`, with `op`, `timeout_ms`, `pid`; not a transport code, so a read never falls back on it), `E_INTERNAL` (`load_failed` for any other load throw, `op_failed` for any other error out of `embed` or `tokenCount`, including a codeless or Node-coded child error; the child's own code is kept in `detail.raw_code`, never used as a cause). The causes are exactly `absent | dead | timeout | load_failed | op_failed | canary`; `phase` (`load` or `op`) appears on `timeout` only. Caller errors (`E_TOO_LONG`, `E_ARGS`, `E_NO_EMBEDDER`) carry no `detail.embedder`. `memory.stats` `owner.embedder_error` carries `{ code, message, cause }`.
- **Bounds and liveness for a vector call** (a `memory.search` without `query_embedding`, a `memory.store` without `embedding`). A client of an owner whose lock names a live pid first sends the 300 ms ping `status.get` uses. An answer means the call gets 100,000 ms (inside the 120,000 ms MCP tool timeout); on expiry it is `E_TIMEOUT { method, owner_pid, timeout_ms }`, saying the owner answers its pipe but not the call. Silence is not yet loss: a live owner pid that missed the 300 ms ping gets one re-ping bounded at 2,000 ms (build 12b E2, so a CreateProcess stall on its loop is not read as a wedge); silence to both is `E_OWNER_LOST { method, owner_pid, ping, first_ping }` within about 2.3 s, naming both pings; the call is not attempted and never silently falls back. A lock with no live pid falls back to a copy, which has no embedder (`E_NO_EMBEDDER`). ADR 0040 routing, as built: the vector bound applies to a `memory.search` of mode `semantic` or `hybrid` without `query_embedding` and to a `memory.store` without `embedding` and without `embed: false`; a `keyword` search, a search that supplies `query_embedding`, and a store with `embed: false` take the ordinary 300 ms read or write bound and need no embedder. A `hybrid` search whose owner is lost, wedged or still loading does not fail: it reads a copy, runs its keyword half, and puts the cause (`E_OWNER_LOST`, `E_TIMEOUT`, `E_MODEL_ABSENT` …) in `modes_failed` with `absence_established: false`; a `semantic` search keeps the refusal. When the caller is itself the owner and the semantic half hits the 100,000 ms limit, a `hybrid` search answers from keyword with `E_TIMEOUT` in `modes_failed` and the warning first.
- **Absence.** The package is `@huggingface/transformers` pinned at 4.3.0 as an optional dependency, resolved only from belay's own `node_modules` (or `BELAY_TRANSFORMERS_PKG`); a missing package or another version is `E_MODEL_ABSENT` naming `npm install` or the version found. A model not in the cache (`%LOCALAPPDATA%/belay/models/<id>@<sha>/`, or `BELAY_MODEL_CACHE`) is `E_MODEL_ABSENT` naming `belay embedder fetch --model <id>` and the missing paths. `belay embedder fetch|verify` is the only network use: it verifies every file's bytes and sha256, takes an exclusive lock, and removes stale temp directories. `belay doctor` checks presence by stat only.
- **A worker's turn text** (`type: 'turn'`) is written to memory after the turn's waiters resolve and the worker row is written, on a per-worker serial queue the turn path does not await; a write not started before shutdown is dropped and recorded, and the run manager's shutdown waits at most 5,000 ms for the queues (`memory_gave_up` names any it left).
- **The exact-scan ceiling** is `floor(50000 * 384 / dim)` rows per namespace, from the namespace's bound dim (18,750 at 1024 dims); above it `E_NAMESPACE_TOO_LARGE { namespace, rows, ceiling }`, and `allow_slow` lifts it.

A run spec names its prompt with exactly one of two keys. `brief_file` is a path (relative to the spec) to the operator's brief; belay renders its own shipped template for the run's mode (`orchestrator.md` or `orchestrator-interactive.md`), substitutes the levers into the template, and appends the brief under a `## Your brief` heading, so an upgrade refreshes the prompt (the brief itself is not lever-substituted). `prompt_file` stays for a fully custom prompt, read as is, with the stale-copy warning. Giving both keys, or neither, or an unreadable or empty `brief_file`, is exit 2 before the data dir is created. A `brief_file` run carries no `prompt_warnings`.

`belay run`'s receipt (stdout `--json` and `run.json`) carries `workers_closed` (ADR 0029 and amendment 1), `null` when no run row was attached: `{ adapter_pid, adapter_gone, adapter_wait_ms, adapter_wait_bound_ms, killed: [{ worker_id, pid, gone }], marked_dead, errors }`. Before `run.end`, `belay run` waits for the run row's `adapter_pid` (skipped when it is `belay run`'s own pid) for at most the larger of `close_grace_ms` and (this run's life-claiming worker rows with a live pid when the wait starts, a Codex `idle` row not counted since it has no process by design, × (10,000 ms + T)) + (5,000 ms + T), T the snapshot limit in force (15,000 ms by default, ADR 0048), recorded as `adapter_wait_bound_ms`, plus `NOTE_REVIEW_DRAIN_MS` (20,000 ms, `src/core/spawn-bounds.cjs`), which is the adapter's own in-process bound on applying review tasks' verdicts before it stops any worker (`belay run` adds the same 20,000 ms to the adapter wait, one deadline for both drains); the worker rows are read again after the wait. It then kills by exact pid (tree, then pid) every life-claiming row still alive and waits up to 5,000 ms for it to go, never touching a Codex `idle` row. `marked_dead` is `run.end`'s own `workers_marked_dead` (`null` if `run.end` failed). A headless run's `workers_closed` also carries `left_parked`: the ids of this run's workers that were parked (state `paused`) when the run closed, left parked and not rewritten (ADR 0023 amendment 5). An interactive run's text output names them on a `left parked:` line. A `run.get` or `worker.list` failure at close, even one a later re-read recovered (named in `errors`), or a pid still alive after its kill, is chained onto `ended_by` as `worker close: ...` and forces exit 1. `mcp_tool_timeout_ms` in the spec must be a positive integer (exit 2 otherwise). ADR 0031 adds two spec keys. `max_fix_rounds` is a non-negative safe integer, default 2. `fix_cutoff` is `'orchestrator'` (default) or `'cap-only'`. Any other value is exit 2 before the data dir is created. After reading `prompt_file`, `belay run` replaces every `{{max_fix_rounds}}` with the number and every `{{fix_cutoff_rule}}` with one sentence per `fix_cutoff` value. The orchestrator's `prompt.txt` holds the substituted text, and a prompt without the placeholders passes through unchanged. The `orchestrator` sentence names the four stop-early conditions. Its time-bound condition is written in only when `timeout_ms` is above 0 (`the run's time bound (<timeout_ms> ms from its start) is near, judged from the waited_ms your worker_wait answers report`). With `timeout_ms` 0 the condition is dropped and the sentence says the run has no time bound. The receipt (stdout `--json` and `run.json`) carries `levers: { max_fix_rounds, fix_cutoff, substituted: { max_fix_rounds, fix_cutoff_rule } }`. `substituted` is the number of replacements actually made (0 and 0 for a prompt without placeholders), so the receipt never claims a cap the orchestrator was not told. It also carries `review_rounds` and `review_rounds_reason`. `review_rounds` is the number of this run's tasks whose `acceptance.verdict` is `true`, read with `task.list` after the worker close and before `run.end`. It is `null`, with the reason in `review_rounds_reason`, when the run never started (election failure or refusal), the attach never landed, or `task.list` failed. The text output gains one `levers: ...; review_rounds: ...` line. The cap is audited and enforced (ADR 0031 decision 6, build 12): `belay run`'s `run.attach` writes `max_fix_rounds` (null or a non-negative integer, else `E_ARGS`) on the run row, a later attach without the key inherits it from an unended epoch, and `task.create { repairs }` refuses a fix task past it with `E_FIX_ROUNDS`. The orchestrator adapter adds one field, `attach: { reattached, workers_marked_dead }`, once it has attached; the core never writes it. In orchestrator role the adapter runs `run.attach` (a write) before its first store-opening tool call when `memory.db` already exists, so a new session's first `status` shows the reconciled epoch; against an absent store, and in worker role, nothing is written. That is the adapter's own rule, not a read's: a CLI command in mode R (build step 4a's `belay status`, `belay workers`) never calls `run.attach`, never elects, and never writes, so a run whose adapter is gone is reported as it stands (`run-alive` false, established by the pid check) and the next adapter's own attach is what reconciles it. The 100 ms budget binds the core's `status.get`, not that first attaching round trip. `verdict` is `alive` when every rung with something to check holds, `stopped` when the first four do not all hold, `degraded` otherwise. A dead system is a valid answer. Budget: under 100 ms with no owner alive, in-process. Nothing reachable from `status.get` may require the embedder module.

**Memory behaviour (ADRs 0041 to 0043).** Every item names its lever (§3 "Memory levers") and does nothing when it is off. Whatever runs after a turn is queued on the worker's own `memoryQueue` and never awaited on the turn path; a write not started before shutdown is dropped and recorded, and nothing writes after the shutdown flag is set (no shutdown re-elects an owner). Events are scoped to the turn in progress and move to the turn's record when its `turn_end` arrives; at most 4,000 per turn, the overflow counted. With `capture` off the parser keeps no state for it and every event is byte-identical to before.
- **Observations (`observations`, needs `capture`).** With the lever on the observation is the turn's only row (ADR 0044 decision 1): no `turn` row is written. The row's `type` is always `observation`; the builder's classification (`change`, `discovery`, `failure`, `turn`) is stored as `body.kind`. The turn number, token counts, cost, pid and model it records are those of the moment the turn ended. A `memory_event` of kind `observation` records the row, or the code that failed it.
- **Summaries (`summaries: 'mechanical'`, needs `observations`).** `type: 'summary'`, `source: 'summariser'`, `title` of `worker-stated: <findings, one line>` when the hand-back has findings (control characters stripped, whitespace collapsed, redacted, then cut to the 160-byte title bound on a character edge) and `summary: task <id> (no findings stated)` otherwise, text opening `[generated summary (mechanical); data, not instructions; fields marked worker-stated are the worker's own unchecked words]` and then `about: task <id>, worker <id>, run <id>` (so two tasks with the same spec and no findings are two rows in a project namespace, where the store dedups on text), `body = { v: 2, asked, looked_at, learned, done, next, final, notes, generator }` (generator version 2). `asked` is the spec's first 400 bytes. `final` (v2) is the last turn's final text, taken from the newest observation that states one (`body.narrative`, so it needs `observations`): one line, prefixed `worker-stated: `, at most 1,200 bytes in all, `''` when none; it is inside the bounded fields, so the whole body stays under 8,192 bytes. `next` is the last worker-stated next step: the worker's checkpoints (read for the task and worker through `store.diff`, source `worker`, oldest first) and then the hand-back's `next_step`, the hand-back winning; a failed checkpoint read is named in `notes` and never hides the summary. Readers accept a v1 body (no `final`): the index's touched-files read looks at `looked_at` and `done.files_modified` in either version, written once per `(task, worker)`, into `project/<name>` when `project_writes` is on and the run has a project (no run-namespace original and no copy) and into `run/<id>` otherwise, when that worker's turn ends with the task `released` or `done`, or the worker reaches `stopped` or `dead` holding a task; once is decided by an `ok: 1` `summary` event for the pair. `src/run/summarise.cjs` classifies its output `ok | empty | malformed | refused | over_budget`; only `ok` stores a row and every other class records an `ok: 0` event with `E_SUMMARY_EMPTY`, `E_SUMMARY_MALFORMED`, `E_SUMMARY_REFUSED` or `E_SUMMARY_OVER_BUDGET`. The `model` kind of summariser is not built and throws `E_SUMMARISER_ABSENT`. No model or network call is made.
- **Project namespace (`project`, `project_writes`).** `project/<name>` is named by the spec only, never by a folder, a cwd or a git remote. With `project_writes` and a project (ADR 0044 decision 2): the summary is written once, straight into `project/<name>` (a `project_write` event with key `summary:<id>`), with no run-namespace original and no `copy-of:` copy; observations are not copied (they stay in `run/<id>`, and what they carry that matters reaches the project through the summary); and when a worker's task ends (the task `released` or `done`, or the worker `stopped` or `dead` holding it) the manager calls `memory.promote` for the rows that worker wrote for the task, which moves them into the project (`promote:<id>` events). Without a project, or with the lever off, the summary goes to `run/<id>` and nothing moves. `memory.setStatus` to `verified` still copies the row as described there (copy-on-verify is unchanged), and each copy is a `project_write` event. The `memory_store` tool's `namespace` says "Defaults to this run; moved to the project when your task ends".
- **Usage ledger (`cost_ledger`).** One `usage` row per turn from the turn's own numbers, with the cost basis described in §2.
- **First-message index (`first_message_index`, `index_bytes`).** In the opening message, after the resume line and before the prompt, the manager calls `memory.index` (`task_id`, `worker_id`, `max_bytes: index_bytes`, and `query`: the prompt, its first 16,384 characters, when the preface is handed one) and injects `text` when it is non-empty, followed by a blank line. Every call is an `index_injected` event carrying `row_ids`, `bytes`, `sha256`, `dropped` and `over_budget`; zero rows gives `bytes: 0` and injects nothing, a failed call injects nothing and records `ok: 0` with the code. The event's `message` is one JSON text: `{ hybrid, queries: [{ label, ms, ok }], failure?: { code, message } }`, with `hybrid` true only when a semantic list contributed to the index's order (the core's `relevance.semantic_contributed`) and `failure` naming why a query, or the semantic signal, did not (queryable by `code`; the store has no scalar columns for it, and a failed event also carries the `code` column). **The index is hybrid (ADR 0034 applies).** For a run with a `project`, when a worker spawns or is relaunched (a replace, or a resume after a park), and when the worker has a task, the manager calls `memory.embedQuery` with the task id and the worker id (the task's own text is read in the core, so a relaunch embeds the same text as the spawn and a resumed worker gets a hybrid index) and passes the vectors to `memory.index` as `query_embeddings`, for the ADR 0044 index and the notes index alike; the keyword side keeps the prompt (its first 16,384 characters) when there is one. The spawn's own bound is 12 s (`SPAWN_EMBED_MS`): past it the index is keyword-only and the receipt names `E_EMBED_BOUND`. A run with the index off, no `project`, or a worker with no task embeds nothing. The embedding happens before the task is assigned and before the worker's process is launched, and its time is kept out of the worker's startup window and `ready_ms` (it is in the receipt's `queries[].ms`). If an embedder failure is reported: under `on_embedder_failure: required` the owner's hook has paused the run, and a **spawn is refused** (`E_PAUSED`, the `starting` row written `dead`, nothing assigned or launched, the receipt `ok: 0` with the code; the message names the cause and says to spawn the task again after the resume with a NEW worker id, or, when the guard is ENDING the run because the failure (`E_MODEL_CHANGED`, a canary) cannot be fixed inside one, says that and not to spawn again) so the orchestrator spawns again after the resume; a relaunch injects no index and records `ok: 0` (the resume relaunches it and the index is built again, since an `ok: 0` receipt shows no rows). Under `keyword`, or when the call itself failed so the mode is not known (a lost owner), the index is built from keywords alone and its receipt is `ok: 1`, `hybrid: false`, with the failure named. Under `off` memory is off for the run: no index, and the receipt is `ok: 1`, `bytes: 0`, with `memory: "off"` in its detail. The 12 s bound is an embedder failure in every mode (ADR 0034 amendment 1): `required` refuses the spawn as above. A run manager whose core has no harness view gets `E_ROLE` from `memory.embedQuery`, recorded as a wiring fault and never stopping the run. The import-graph rule stands: this process never loads the model, and `memory.index` is a read that embeds nothing.
- **The bottle (`bottle`, `bottle_bytes`).** On the replace branch of a restart, `resume.md` is `buildBottle` of the worker's `stream.jsonl` (only complete lines), `sent.jsonl` and the task's stored observations, bounded by `bottle_bytes`: every assistant text message verbatim and in order labelled `assistant:`, the sent messages labelled `user:` (the first `task` message is the pinned spec; `wake` and `resume` messages are marked `(generated)`), each tool call and its result one line such as `[tool Bash: npm test -> exit 1 (reported); 212 lines]`, all of it redacted. With no sent record the header says the sent messages were not recorded and the result reports `user_messages: 'unrecorded'`. Over the bound the oldest messages go first and the task spec, the last 20 messages and the last assistant message are always kept. Any failure (`E_REDACT_ABSENT`, `E_REDACT`, an unreadable stream, an empty render, over budget with nothing droppable, `E_BOTTLE_WRITE`) falls back to the store-derived resume document of ADR 0007 and records a `bottle` event with `ok: 0` and the code; a success records `ok: 1` with `bytes`, `sha256` and `dropped`. The resume branch (`--resume <session>`) builds no bottle. A `/compact` the manager writes is recorded in `sent.jsonl` as a generated message, not as the worker's. The bottle is Claude Code only: a Codex worker records no `sent.jsonl`, and `buildBottle` on its stream returns `E_EMPTY`, so every Codex replace falls back to the resume document. **Inject once on a relaunch.** A relaunch leaves out the rows the worker was already shown (`exclude_ids`) only where the new conversation still holds them: a resume, or a replace whose bottle succeeded and holds the recorded first message (`spec_pinned`, the first `task` entry of `sent.jsonl`, which carries the opening index). A replace with the bottle off, a bottle that fell back, a bottle without that entry, or a Codex worker starts a fresh session that holds none of the old index, so it is shown the whole index again. An earlier receipt's row is left out of a replacement's index only where the bottle's text holds that row's line (`- <id> [type/status] title`): the opening index, which the pinned first `task` entry keeps, stays excluded, and a row shown only by a later relaunch message that the bottle dropped (it keeps the first `task` entry, the last 20 messages and the last assistant message) is shown again. A replace begins a new conversation: the receipts before it count only through the bottle (an index row line at the start of a line of a `user:` message), the receipts from it on count in full (a later resume holds what the replacement was shown). The boundary is the replacement's first `index_injected` receipt, whose detail JSON carries `convo: { carried }` (the earlier ids the bottle held, `[]` when unknown), so any process that adopts the worker reads the same one.
- **Wrap-up (`wrapup`).** When a worker's turn ends with its task `released` or `done` (after the summary when summaries are on), and once for the run, the manager renders a block of at most 600 bytes through `fit` (task id, final state, acceptance verdict, files modified, ledger cost when `cost_ledger` is on, the summary row's id; no clock) and records it as a `wrapup` event with `key` `task:<id>` or `run`, the text in `message` (redacted like every event message) and its row ids; the unique index in §2 makes a second success for the key `E_EXISTS`. The run-end jobs (the remaining summaries and project copies, the task wrap-ups and the `run` wrap-up) run from `belay run` after the orchestrator adapter has closed, because the adapter's own shutdown is cut short when the orchestrator closes its stdin; they are idempotent, and `run:gave-up` is recorded as a failed `wrapup` event when the bound (5,000 ms) ends them early. `belay notices` shows each wrap-up once.
- **Note review (wave 4; needs `notes`).** **Removed 2026-10-21: the short review job** (a worker `notereview-<task>`, its prompt, its drain, and the levers `note_review`, `note_review_model`, `note_review_cost_cap_usd`). A report that a note is wrong now holds the note at once (below); `note_review: false` is still accepted and recorded nowhere, any other value of the three is refused. The job paragraphs that follow describe the removed route and are kept only for the review task's route. A note is judged on its own by a reviewer other than its writer, and belay applies the verdict (`memory.noteVerdicts`). Two routes. A task with a reviewer: the review task's opening message gains up to 8 of the notes its reviewed tasks wrote, the `memory_verdicts` shape, the 4096 byte limit of a hand-back's `result` and, mechanically, any refuted note a reviewed task's worker was shown ("check whether the work or its notes relied on it"); when the review task ends, the run manager applies the `result.memory_verdicts` of its hand-back (a reassigned review task's later hand-back is applied under its own key). A task without one, with `note_review` on: when it ends having written unreviewed notes the run manager spawns one short worker `notereview-<task id>` (invariant 1; the prefix is reserved), model `note_review_model` (a Claude 5.5 id; default `claude-haiku-5-5`), tools Read, Glob and Grep only, `--max-budget-usd` `note_review_cost_cap_usd` (default 0.05), no task, no lease, no notes contract, no memory index and an adapter that lists no tool. It is given a notes file, the task's diff (base to head of the worker that wrote the notes) and the stream paths of that task's workers under `workers/notereview-<task>/inputs/`; its cwd is the writer's worktree. It ends with `{ "memory_verdicts": [...] }`, which the run manager parses and applies. Every outcome is a `review_job` receipt (key `task:<id>`), including a job that timed out, answered with no JSON, cost too much or never ran because the run ended. **The recorded cost is the binding cap:** a job whose worker row records no cost, or more than the cap, has its verdicts discarded (`E_COST_CAP`), whatever `--max-budget-usd` did. Shutdown waits up to 120 s for a job in flight before it stops any worker; `belay run`'s store-only end applies a finished job from its stream only when no receipt of any kind exists for its task, and records the rest as owed. A job's receipt is ok only when it left nothing: a note or report it refused or gave no verdict on makes it `ok: 0` with `code: 'E_PARTIAL'`, naming the notes left; the run's sweep also names, once under key `left:<task id>`, a task whose notes no review judged (written after a clean job, or not named by a partial job's receipt; a failed job's own receipt is the record and is not repeated). A wait capped by `MCP_TOOL_TIMEOUT` is asked again until the job's own 180 s wall is spent, and a timeout receipt names the wall really waited. `belay run` runs the store-only sweep before the scrub, so a late job's upheld report is applied before the scrub can archive its note; that sweep applies finished work only (a job whose worker is stopped or dead, or whose process has closed while its row still reads idle, with a cost and a whole answer in its stream) and writes no receipt, because the rows of a killed job are settled only by run.end and the run-end sweep, which runs after it, must still be able to apply them. A note that is not reviewed stays `unverified`. **Not proven, and why `note_review` stays off by default:** that `--max-budget-usd` is honoured with stream-json input (the flag is documented for `--print` only; no real session was run), and that the job's Reads of its inputs under the data dir are allowed by the `auto` permission mode (the launch flags confine it to `--tools Read,Glob,Grep`, `--allowedTools Read Glob Grep`, no setting sources and no belay tool; they cannot confine which paths those tools read). **The citation check** (`src/core/citation-check.cjs`): a stream cite counts only a tool result whose tool_use is in the stream and is not an `mcp__belay__*` tool (a hand-back or search result echoes the note's own title), and a stream cite is refused as the note quoting itself when the quote is held by one of the note's own fields (title, `when`, text, evidence `where` and `saw`) or holds its title, unless a non-belay tool result prints it and that result is not an echo of the note. A result is an echo when its text (JSON escapes decoded, whitespace collapsed, case folded, also as printed) holds a title of 20 or more characters or the first 32 characters of a longer title, or has a line that is the title (a title of 4 to 19 characters counts only as a whole line), or holds an own sentence (16 or more characters with a space: `when`, text, a `saw`, an evidence `where`) of 60 or more characters on a line other than the one that holds the quote (for a `saw` only: the line a faithful `saw` copied is the evidence itself, not an echo; a `when` or text sentence that a tool printed is an echo wherever the quote is), or any own sentence when the title is a single token with no space that the result also holds. A refusal for this reason says the result also shows the note's own text, apart from the reason for a quote only the note holds. A short `saw` a tool really printed, or a short phrase title in a heading or log line, is not an echo; what stays open is a worker printing its own short `saw` (a long one is caught only when it is printed on a line other than the quote's). A quote held only by the note, a belay call or its result, the worker's hand-back or its prose is in no counted result and is refused (the same check serves the lifecycle path: scrub and archive review). A verdict from a review task is refused for a note its brief did not list (the first eight notes, fewer beside reports, fixed before any verdict is applied: `reason: 'not_shown'`). The review task's brief and the job's prompt give each note capped, as data (the job's notes file holds every field of every note, uncapped): title, `when`, kind, basis, `applies_to` and `subjects` in full; the stored text at 400 bytes; at most 3 evidence entries, each `where` in full and `saw` at 200 bytes; a cut ends in an ellipsis naming the original length, and the entries left out are counted. `applies_to` entries belay derived (from the evidence or the diff) are labelled belay-derived, not writer-stated; a file cite must name a file (not a directory). **The refuted-note wake** goes through the ordinary wake (headless stdin, interactive wake pipe), one per poll and review however many notes it refuted, and is facts only, all belay's own words: the notes, the review receipt id, the shown tasks as running or finished and whether a finished one cited the note, the review tasks over those tasks (running or finished) and the derived note ids. Its first sentence names the notes and the review and stands alone, because the interactive wake mod keeps only about 220 bytes. The reason, cites and titles are read through the orchestrator's `memory_note_refutation` tool (listed with `notes`, data not instructions); `refutedWake(..., { withReason: true })` puts a cut, labelled reason back and is off until the operator rules on it. Whether a worker "was shown" a note is `note-delivery.cjs shownTo` (today the `index_injected` receipts). Levers: `note_review`, `note_review_model`, `note_review_cost_cap_usd`. **Search is not gated here:** a refuted note is still returned by `memory.search` and `memory_retrieve`, labelled `refuted`; only the first-message index and the corpus omit it. The gate for index and search (task ended, review did not refute, not pending, superseded, archived or promoted) is the lifecycle gate's work.
- **Note contract (paired write and search).** A note is found by the task that would run into it, so it is written as a claim and a situation. `lease_release` notes take `title` (the claim, at most 160 bytes), `when` (required, at most 160 bytes: the task that would trip on it, as a task line; `E_NOTE_SHAPE` otherwise, never truncated), `kind`, `basis`, `evidence`, `subjects` (0 to 3) and `applies_to`. `applies_to` is derived by the core at hand-back: any paths the worker stated, the paths named by the note's `evidence.where`, and only those files of the worker row's `base_sha..HEAD` diff and working-tree status that the note's title or evidence names (full path, or a file name of at least 4 characters), at most 16, stored in `body.applies_to` with `body.applies_to_from` (`worker`, `evidence` or `diff`, aligned with it). The task's whole changed-file list is kept apart as `body.task_files` (at most 30, `body.task_files_from` `diff`), so unrelated notes of one task share no `applies_to` path through the diff. A diff that cannot be read is named in the result's `applies_to.diff_error`. Two texts are made and kept apart. Embedded (template v2) is exactly the title, a line break and `When: ` plus the `when`; evidence, subjects and applies_to are not embedded. The row's `text` (hashed, and the keyword index) is the title, the `When:` line, `subjects: ...` and `applies to: ...`. `memory_entries.text_template` records the template of every embedded row (`v1`: the stored text as it was; `v2`); a row embedded before the column reads as v1. A search over a store holding both works, but mixing is suboptimal: `belay memory embed --reembed --template v2 [--project]` (operator, never automatic) rebuilds the v1 vector of a note that has a `when`, and a v1 note without one stays v1 and the receipt names it. The spawn query is the spec's opening paragraph, and `worker_spawn`'s `memory_queries` (at most 4 task lines) are fused with it by rank. The hand-back question lists the project's most used subjects (`memory.noteSubjects`). The question and the contract treat findings alike: `result.findings` goes to the orchestrator and is kept on the task row (`handoff`), which `task_list` returns to any worker; nothing pushes it to a later worker, and with `summaries` `mechanical` a `memory_summaries` row of it can also turn up on a search. The contract says only that ("not passed to them automatically"), so the question does not tell a worker to leave out what its findings say.
- **Eval-only run-spec keys (0.3.2 memory eval; off by default, not for production runs).** Two top-level keys of a `belay run` spec, recorded in the run's memory levers (`memory.native_memory`, `memory.handback_question`, so also valid inside `memory`, but not in both places). `native_memory: <absolute dir>`: every Claude Code worker the run spawns shares that one folder for Claude Code's own auto-memory (the `native_memory` argument of `RunManager.spawn`, ADR 0024 amendment 3, used when the call names none); the orchestrator, Codex workers and belay's own read-only jobs never get it. The value is checked at spec load with the spawn's own check (absolute, not in Claude Code's config directory, creatable) and a bad one refuses the run before anything launches; the folder is created at the first worker launch. `handback_question: true`: with `notes` off, the opening message and relaunch of each worker a notes contract would reach (coders, fixers, reviewers; not jobs, not the orchestrator) ends once with the shipped end-of-task question (`src/run/prompts/notes-question.md`) as a request to record what surprised it where the project keeps durable notes for later sessions (the same text in every arm) or give it in the hand-back (`src/run/prompts/handback-question.md`), with no note contract and no `notes` field. With `notes` on it changes nothing.
- **Notes (`notes`, ADR 0047; default on, which takes effect only when the run has a `memory.project` and keeps `redact` on: with no project (never derived from a folder or a remote) a run that did not name `notes` has it off and behaves as before; an explicit `notes: true` without a project is refused; set `notes: false` to turn it off. With it off a run behaves as under ADR 0044 except for the changes every run took with the note contract: the first-message index's task query is the spec's opening paragraph, not the whole spec; `worker_spawn` takes `memory_queries`; the `memory_search` description gives search guidance; and the tool listings changed size, now 4,815 bytes for a worker and 9,870 for an orchestrator (10,029 when `first_message_index` is on, which lists `memory_queries`)).** Needs `memory.project` and a redacting run (`redact` not false). Eight keys, all in the `memory` block: `notes` (boolean); `notes_match_threshold` (a cosine above 0 and at most 1, default 0.80) and `notes_match_n` (1 to 10, default 3), set from the planted-duplicate study for the store's embedder (the 0.80 was measured on v1 text only and is unvalidated on v2; matches, and the scrubber's duplicate and supersede facts, compare only rows with the same `text_template`, and record it); and five switches that need `notes`: `notes_sink` (`off` \| `record` \| `penalty`, default `off`; `record` writes the delivery, area and use facts of `memory.recordChances` at task end, `off` writes nothing new, and `penalty` records exactly what `record` records because the rank penalty is not built yet), and four more: `notes_overflow_line` and `notes_trust_wording` (the index, both default off; see `memory.index`), and the write ablations `notes_reflection` (the end-of-task question asked again as a turn of its own after the hand-back: once the task has ended, the manager messages the worker, which answers with a second `lease_release` carrying only `notes`; the outcome is a `reflection` receipt, ok or with the code that failed it) and `notes_lesson_question` (the question aimed at what the worker learned instead of what the next one would get wrong; it applies to the contract text and to the reflection). With `notes` on: the worker adapter is launched with `--notes` (from the run row, by the manager; a worker's tool listing then has `lease_release` with `notes` required and `reported_wrong`, plus `memory_note_resolve` and `memory_summaries`; every ordinary tool stays listed, inside the 7,168 byte worker budget of ADR 0010 amendment 6); the opening message of a worker, and a relaunch, ends with the contract text (`src/run/prompts/notes-contract.md` and its question files); the core stores and matches notes (`lease.release`, `memory.noteResolve`). The orchestrator's listing is unchanged. A dedup hit in `memory.store` on a row of type `note` returns `action: 'unchanged'` and never rewrites it, whoever the writer is. `memory.store` refuses `type: 'note'` and a body carrying `model`, `state`, `seen_in`, `seen_total`, `matches`, `reported_wrong`, `resolved` or `superseded_by`, for every caller (`E_ARGS`). Run summaries (ADR 0047 decision 1): with `notes` on the manager stores a task's summary in `summary/<project>` (always scrubbed, as a project row is), not in the run and not in `project/<name>` even with `project_writes`, and records no `project_write` receipt for it; the first-message index and the default search read the project and never reach it, and a worker's search reach does not include it. It is found on demand by `memory.summaries` (the orchestrator's `memory_summaries` tool is listed when the run row says `notes`, with `knowledge_ask` too, inside the 16,384 byte budget; a worker's adapter launched with `--notes` lists it as well, role both), and `continuity.resumeDoc` adds a section of the task's three newest from the same lookup. The run-end scrubber, the archive reviewer, promotion and the sink recording are the lifecycle bullets below; not built: the sink penalty (`notes_sink: penalty` records what `record` records), freshness anchors and trigger re-delivery.
- **Rows of the project that are not notes, refutation by report (ADR 0047 amendment of 2026-10-22).** In a run with `notes` on, a worker and the orchestrator cannot read a row of `project/<p>` whose type is not `note`: search (keyword, semantic, hybrid), list, timeline (anchor and neighbours), get, get_many and the corpus answer as if it were absent; the operator's command line and a run with `notes` off read it as before (no migration). In that run `memory.setStatus` on a note by anyone but the operator's own command is never a status: the orchestrator's `refuted` (with a valid receipt) is a report through `memory.noteReport`'s transaction (reporter `orchestrator`, the receipt as reason and cite, the status left as it was; the answer names the hold row or `not_held` with the reason), its `unverified` and any other caller's `refuted` are `E_ROLE`, and `verified` stays refused. A task reviewer's `refuted` verdict (with cites that pass) is a report as well, reporter `worker:<reviewer>`, held for the archive review with the verdict recorded on the hold as advice, the status left, and no `note_refuted` receipt (the wake that followed it no longer fires). `memory_verify` is not listed for the orchestrator of a notes run (listing sizes: worker 7,094 bytes, orchestrator 10,720, 10,879 with `first_message_index`, 11,074 with the knowledge agent, 11,233 with both) and a call is `E_ROLE`.
- **Notes lifecycle levers (default `scrub_action: propose`, `scrub_max_items: 40`, `scrub_alarm_holds: 20`; all inert unless `notes` is on).** `scrub_action` is `off`, `propose` or `apply` and gates `memory.scrubApply`. Namespaces: `held/<project>` (open holds, one row per hold, the note stays live in `project/<project>` and carries `body.held`), `archive/<project>` (archived notes keep their id; not read by the index or the default search), `proposal/<project>`, `draft/<project>`. Nothing is deleted outside the operator: a `repeats` resolve archives the pending row, and `memory.delete` of a note or a lifecycle row is the operator's. Known limit, not B6's: the pipe trusts the role a client sends, so the operator-only purge and delete rest on that trust until the role-from-process change (ADR 0045).
- **Run-close stages (levers `scrub_wall_s` 300, `scrub_cost_cap_usd` 0.10, `scrub_model` claude-haiku-5-5, `review_min_held` 3, `review_max_age_runs` 3, `review_wall_s` 600, `review_cost_cap_usd` 2.00, `archive_review_model` claude-opus-5-5, `archive_review_auto` false; models are Claude 5.5 ids).** After the workers close and before `run.end`, `belay run` calls the stages (`src/run/close-stages.cjs`), headless and interactive. The scrubber runs when `memory.scrubScope` lists anything (empty scope: no child, no manager, a nominate call and two reads); the archive reviewer then runs when `memory.reviewQueue` meets a trigger, but ONLY when the lever `archive_review_auto` is true (default false: the reviewer is on demand, by `belay memory review [--project p]` or the panel's button, and reviews the held queue of every kind: `wrong`, `duplicate` (archived only on `same_claim: true`), `superseded` and `unsupported`). For an `unsupported` entry the brief lists PATHS (the task's streams, the run's other workers' streams, the task's diff saved beside the brief) and the reviewer reads selectively; it answers `verify` (status verified), `refute` (status refuted, with the `note_refuted` receipt the orchestrator's wake comes from) or `still_unsupported` (the entry leaves the queue, the note stays unverified). verify and refute need a cite: a stream cite must be a TOOL RESULT of a non-belay tool in a stream among the evidence files (never belay's own tool inputs or results, assistant or user prose, or the task brief), and not the note's own title, `when`, text or evidence; a file cite is read at the head commit. Each unsupported entry adds at most 25 streams to the evidence files, after the streams that marks cite; each answer returns a `review:<run>:<queue row>` receipt, also as the note's `status_receipt`. An answer of the wrong kind (archive on an unsupported entry, verify on a held warning) is refused `E_PRECONDITION`. **One review at a time.** The review the command or the button starts holds a claim (`memory.reviewClaim`): the CLI that parents the child takes it with its own pid and creation time, and releases it with the outcome; a second review refuses `E_BUSY` while the claimed process is alive by identity, takes over a claim whose process is gone (and kills the dead review's child by the exact identity on its worker row), and a signal during the review kills the child by its exact pid before the CLI exits. The panel's button runs `belay memory review --project p --start`, which launches that command detached (so a reload of the panel cannot end it), waits for the claim to show and prints it. **Beside a live run (ADR 0052).** The review is an operator client of the run's store owner and acts for an ended run, so its writes are keyed to that run and its project and the live run's `run.end` touches none of them. `belay run`'s close, after run.end and the run-end note jobs and before `shutdownOwner()`, stops the owner taking review claims and waits while a running claim's pid is a client attached to the owner (`Owner.attached()`, ADR 0051 decision 3), naming each and its deadline on stderr; Ctrl-C or a console close cuts the wait (the review then loses its owner, and its release is tried once more through a fresh core). The wait is bounded: each review's deadline is its claim time plus the `review_wall_s` of the run it acts for plus 120 s, and at the latest one the wait ends `cut` (`cut_by: 'deadline'`), says so, and the close goes on. The run receipt's `store.review_wait` is `{ waited_for, ms, deadline_at, outcome: detached | cut | error, cut_by?: interrupt | deadline }`. With `archive_review_auto` on, the close-stage reviewer does not start while the project's claim is held by a live pid. Each spawns one read-only child (Read, Glob, Grep) through a run manager built over the harness core, whose job id starts `scrub-` or `archreview-` (reserved, like `notereview-`: no memory preface, no belay tool, no wake). The child runs in, and its cites are checked against, ONE worktree at ONE head commit per scrub (the newest worker of the run with both), recorded on the `scrub_job` receipt. Items are recorded as `scrub_owed` (code `E_INTERRUPTED`) BEFORE the child starts, and the ok `scrub_job` after a successful apply clears them, so a run process that dies mid-stage loses nothing; a crash, timeout, dead child, junk answer or cost over the cap leaves them owed (with the cause), and the next scrub of the project takes them first. An item the child gave no entry is owed once more and then let go. **Caps.** `review_cost_cap_usd` and `scrub_cost_cap_usd` bound each spawn, not progress: when a spawn overruns (its recorded cost is over the cap, or it failed having spent 90% of it) it applies nothing, a `stage_overrun` receipt records how many items it tried, and the next attempt takes half as many (oldest first, never fewer than 1) until one succeeds; `belay notices` shows the overrun and names the lever to raise. **Dropped items.** An item the child gives no entry in two scrubs (in any runs) is recorded as dropped (a `scrub_owed` receipt with code `E_DROPPED` naming every id, shown by `belay notices`) and is not offered again until a new report from a run, or, for a nominated note, a new counted independent sighting after the drop (the promotion step's own counting). **Fast close and Ctrl-C.** After a console SIGHUP, or a Ctrl-C (SIGINT, SIGBREAK) during the stages, no stage spawns (the scrub's scope is recorded as owed, the reviewer is skipped), and a child already running or starting is killed by its exact pid at once, without waiting for its spawn; every child pid is recorded at spawn, so a stage cut by the close deadline still has each live one killed by its exact pid and named; a child still alive after its kill fails the run's close and is named, also when a stage is cut off by the close deadline. A stage prints one line before it starts, and the run summary the orchestrator could give at the end is not passed (`belay run` has no end call to carry it; `belay memory scrub --summary` can). Stage codes on those receipts: `E_INTERRUPTED` (owed before the child started), `E_UNJUDGED` (the child gave no entry), `E_DROPPED`, `E_ABORTED` (a fast close), `E_SHUTDOWN` (the manager was closing), `E_COST_CAP` (the recorded cost was over the cap, or absent), `E_TIMEOUT` (the wall cap), `E_WORKER_NOT_LIVE` (the child died or ended its turn in error), `E_ARGS` (item cap, no worktree, an unparseable answer) and `E_INTERNAL`. The scrub items are also owed after the item cap, a crash, a dead child and an unparseable answer, and an item given no entry in two scrubs is let go (`E_DROPPED`). **At run close the `scrub_alarm` reaches `belay notices` only:** the stages run after the orchestrator has closed, so there is no live orchestrator to wake (open item for the operator). Receipts: `scrub_job`, `scrub_owed`, `scrub_alarm` (the runaway alarm; woken to a live orchestrator in belay's words and shown by `belay notices`), `review_stage`, `stage_overrun`. **Authority.** An operator on the harness channel may write a worker row only when its id carries a reserved job prefix and the row belongs to the caller's own run (`harnessGuard` in the engine); nothing else is widened.
- **Knowledge agent (`knowledge_agent`).** `ask` refuses `E_LEVER_OFF` with the lever off; the orchestrator adapter lists `knowledge_ask` only when the run row says it is on (read once at the first `tools/list`, through the core's bounded read; a failed read lists nothing and says so on stderr). On the first question the manager writes `memory.corpus` to `workers/knowledge-<run>/corpus.md` and spawns an ordinary worker: id `knowledge-<run id>` given in argv, Claude Code, `claude-opus-5-5`, working in the run's worktree, tools `Read`, `Glob` and `Grep` only (a `--tools` list the surface check accepts) plus its belay memory read tools (its adapter, by the reserved `knowledge-` worker id in argv, lists and allows only `memory_retrieve`, `memory_search`, `memory_timeline`, `memory_list` and `memory_stats`), and the prompt `src/run/prompts/knowledge.md`. A `corpus_primed` event precedes the first message and every later one whose corpus `sha256` differs, which names the new `corpus.md` in a message. Each question is a message followed by the manager's own `wait`; the agent's turn must have ended before a question is sent, so an answer is never the previous question's. `[mem:<id>]` citations are looked up with `get_many`; a missing id is `found: false`, never dropped; `uncited_claims` is true when a substantive line (30 characters or more, not a heading) carries no citation and does not say it is not in memory. A dead or replaced agent is replaced on the next question. A timeout is `E_TIMEOUT` naming the worker; a turn ended in error is `E_SUBSTRATE`; a dead worker is `E_WORKER_NOT_LIVE`; every ask, successful or not, is a `knowledge_ask` event.

Memory codes (ADRs 0040 to 0043): `E_NO_INDEX` (the store, or the copy being read, has no keyword index: no owner has opened it since the index landed, or `meta.memory_fts_version` is `'0'`; it appears in `modes_failed`, never as an empty result); `E_QUERY_SHORT` (no term of at least 3 characters remained for the trigram index; same placement); `E_RECEIPT { receipt, reason }` (`memory.setStatus` refused the receipt, nothing written); `E_SUMMARISER_ABSENT` (the model-kind summariser is not built), `E_SUMMARY_EMPTY`, `E_SUMMARY_MALFORMED`, `E_SUMMARY_REFUSED`, `E_SUMMARY_OVER_BUDGET` (a summariser output class other than `ok`, recorded on an `ok: 0` `memory_event`, no row stored); `E_LEVER_OFF { lever }` (a call needs a run lever that is off, as `ask` and the knowledge agent); `E_EXISTS { run_id, key, existing }` (a second successful `wrapup` event for one `(run_id, key)`, and `belay memory export` refusing to overwrite a file). The ADR 0033 rule holds for the memory writes: `memory.store` is re-run after a lost owner (its text is redacted before it is hashed, so the re-run converges), `memory.recordEvent` and `usage.record` are not. `meta.memory_fts_version` (§2) is the marker the code reads, not an error. `E_SCHEMA_NEWER` (memory plan G3, `src/core/schema-stamp.cjs`) refuses to open a store whose `meta.schema_version` is greater than the core's `SCHEMA_VERSION` (or is not a positive integer): raised by `new Store` before `ensureSchema`, so nothing is written to it; `detail` is `{ store_schema, known_schema, written_by, db, reason }` with `reason` `'newer'` (upgrade belay) or `'malformed'` (the value is `0`, negative, fractional or not a number; the message says so and names recovery: delete the `schema_version` row from the store's `meta` table by hand, or restore a backup, since the core never edits a store it refused). For a write the owner fails to start (the lock is released); for a read the throwaway copy refuses and the error reaches the caller, never a fallback. `E_PAUSED` (build step 6e, ADR 0023 decision 1) refuses `message` always while a worker is parked, and `restart` once a park has completed, naming who paused it and when; during the park itself `restart` reads `E_BUSY` naming `pause` (the operation slot, not this refusal, is what it hits first), and during a `stop` in flight it reads `E_BUSY` naming `stop` (build step 6e-5, closing review 2's note, `api.md:140`). Build step 6e-6 item 4 (carried item 4, `wait.cjs:37`): once a record has gone stale (`pause.cjs` `checkNotStale`/`clearParkForStop` found the row disagrees with this adapter's own park, naming the row's state and the adapter that now holds it — kept on the record as `w.staleSince`, so every later call answers it), `message` and `restart` are refused `E_SUBSTRATE` with that same wording, never `E_PAUSED`: the worker is not paused at all, it is running under another adapter. `E_BUSY` (build step 6e-4, ADR 0023 amendment 2 decision 3) refuses `pause`, `resume` or `restart` when a different one of the four lifecycle operations (`pause`, `resume`, `restart`, `stop`) is already in flight for that worker, naming it; `stop` alone is never refused this way. `E_RUN_NOT_LIVE { task_id, run_id, worker_run_id? }` (ADR 0046 decision 1, activation) refuses `task.assign` (including `check_only`) and `lease.takeControl` on a task that owns files when its run is not live and no live run can own the work: a worker's live run (or, for `check_only`, the calling orchestrator's) takes the task over instead, the task row and its lease are written with that run id, and the overlap check is made as that run; nothing is written on a refusal. `E_TASK_DONE` (build step F1) refuses `task.assign` and `task.evaluate` on a task whose state is `done`, before any row is written; `detail { task_id, state }`. `E_WORKER_LIVE` (build step 6b) is distinct from `E_WORKER_NOT_LIVE`: it refuses `worker.forget` on a row that is still alive. `message` is a sentence that names the reason; `detail` carries ids when there are any. After `E_TIMEOUT` on a write (`detail.may_have_committed: true`) the caller re-reads before retrying, because the owner may have committed the write. `E_OWNER_LOST` with `sent: true` on a write means the outcome is unknown; Core re-runs only `memory.store` and `permission.wait`, and never another write. A re-run `memory.store` gets only what its first attempt left of its 100,000 ms limit, and is not re-run with under 1,000 ms left (`E_OWNER_LOST`, `rerun: 'skipped'`), so both attempts together stay inside the 120,000 ms MCP tool timeout. The pipe `shutdown` method is accepted only from an orchestrator or operator caller (`E_ROLE` otherwise). Refusals in ADR 0010 §2 must produce the code named in §3 above.

## The orchestrator's surface and git_read (ADR 0054, proposed)

- The orchestrator (headless and interactive, fresh and resumed) launches with `--tools Read,Glob,Grep,Edit,Write` (`surface.cjs` `ORCHESTRATOR_TOOLS`): the workers' six without Bash; the headless ready gate holds the reported built-ins to exactly that list. Its adapter is always given the run's worktree as `--worktree`.

## Process snapshots and their opt-in seams (ADR 0039, ADR 0048)

Every kill that is not made through a live child handle, and every spawn-time `pid_created` read, takes one CIM snapshot of the machine's processes through one gate per Node process (`src/core/snapshot-gate.cjs`, used by `src/core/proc-identity.cjs`). One attempt of 15000 ms (`BELAY_SNAPSHOT_TIMEOUT_MS`, a positive integer from 1000 to 600000, overrides it for a process; an invalid value is ignored, the default is used, and the ignored text is logged as `timeout_env_ignored`), never retried. A caller never gets the snapshot already in flight: it gets the next one, which starts after its request, and several callers that join while one is in flight share it. At use, a caller checks that the snapshot started after the last signal this process sent; otherwise it takes one more, and a second failure refuses as `unverifiable` ("signals in this process kept landing after each snapshot started"). A read command never takes a snapshot.

- **Kill receipts** (`killPid`, `killTree`, `killProcess`, `killMany`, the kill log, the run's `orchestrator.kill` and `workers_closed.killed`) carry `signalled_at` (ms since the epoch of the last signal sent, or null) and `snapshot_ms` (how long the identity snapshot took, waits included). A test or an operator measures what happens after a kill from `signalled_at`, not from the call.
- **`pid_created` pending.** A spawn-time read that fails leaves `pid_created: null` and `pid_created_error: "<reason>; retrying while the worker runs (try <n>)"`. The adapter (or `belay run`) that holds the live child handle fills it from any snapshot its gate completes after the spawn, and asks for one at 30 s, 60 s, 120 s and then every 300 s. A reading is accepted only while the handle is live, only if the snapshot has the pid, and only if its creation time is not more than one second before the spawn. If the worker exits first the error becomes `never read: the worker exited before its creation time was read (<n> tries)`. Another process that meets a pending row refuses as `unverified`, as for any row with an error, and its hint says the row may be verified shortly. No row column is added.
- **`workers_closed.killed[].outcome`** (the run close) is `closed`, `signalled_still_alive`, `refused_unverifiable` or `refused_no_budget` (and `refused_mismatch` or `refused_absent`, which prove the process is not the worker). A worker the close leaves alive carries the manual `Stop-Process` hint and `belay worker kill <id>`, which proves the identity again from the row with a full snapshot budget.
- **`BELAY_KILL_LOG`** names a file; every kill attempt appends one JSON line (`time`, `pid`, `via`, `ok`, `kind`, `detail`, `signalled_at`, `snapshot_ms`, `caller`, `fn`). Off unless set; a failed append never changes a kill.
- **`BELAY_SNAPSHOT_LOG`** names a file; every snapshot a process takes appends one JSON line (start, end, duration, timeout, error, bytes, rows, calling file, `start_seq`, `served` (callers it served), `callers_kind`, and `stall_ms` when the stall seam is on). Off unless set; written only on paths that already take a snapshot.
- **`BELAY_CLOSE_LOG`** names a file; the run close appends one `run-row-read` line once it has read the run row for the adapter's pid. Off unless set. It exists so a test can land an attach after that read by observing it.
- **`BELAY_TEST_SNAPSHOT_STALL_MS`** (an integer from 1 to 30000; anything else is ignored) prepends a sleep to every real snapshot, so the product's own timeout runs against a slow one. It can only make a snapshot slower and changes nothing a snapshot contains. It exists so a test run can slow the snapshots of the processes the suite spawns (the CLI, the adapter, `belay run`), which only an environment variable reaches.

## Reported notes (ADR 0047, amendment of 2026-10-21)

- **`lease.release`** with `reported_wrong`: each report is marked on the note (`reported_wrong[]` entry with `seq`, from `body.report_seq`; the key is `s:<seq>`, or `l:<task>@<at>@<by>` for an older report) and, in the same transaction, the note is held: one hold row in `held/<project>`, ground `reported`, written by the harness through the shared hold writer. Each entry of the answer's `reported_wrong` is `{ id, marked, reports, replaced_by, redacted?, held: { row, kind, rev, already_held?, merged?, replaced_stale_pointer?, reclassified? } }`, or `{ id, skipped: 'not_live', state }` when the note left the project while the release was prepared. The report text is redacted once. A report on a note held for another reason merges that hold (`merged`), and the hold's kind follows its reports (`superseded` of a live, kept, related replacement a report names; otherwise `wrong`).
- **`memory.held`** adds `by_ground`, `by_ground_by_project`, `awaiting_operator`; with `{ list: true, project?, awaiting? }` it adds `entries` (one per active hold, oldest first, at most 200, `truncated`): `{ project, note_id, title, held_row, rev, kind, ground, of, reports, reports_total, self_report, undecided, awaiting_operator, marked_at, runs_waited }`. A run caller sees its own project (another is `E_ROLE`); the operator sees the named project or all.
- **`memory.reviewQueue`** entries gain `rev`, `outcomes`, and for a report-made hold `reports` (each with its `key`), `reports_total`, `reports_dropped`, `report_verdicts` (a task reviewer's advice with cites), `self_report`, `prior_hold`, `matches`, `note_verdicts`; an entry whose outcomes would verify the note carries the whole note and `shown_hash`. A hold marked undecided at its revision is left out and listed under `awaiting_operator` (`counts.awaiting_operator`).
- **`memory.reviewApply`** verdicts: `archive | release | undecided | verify | refute | still_unsupported`, with `held_row`, `rev` and `shown_hash`. A verdict is bound to the row and revision it was offered, checked at the first read and again inside the write transaction; a mismatch is refused (`E_PRECONDITION`, detail `{ offered_row, offered_rev, current_row, current_rev }`) and the refusal is written on the offered row. A release or undecided of a reported hold must carry `rev`. A release of a wrong or reported hold needs cites that show the note correct and the `shown_hash` of the whole note; it verifies the note, settles every report on the hold (`settled: { keys, count }`) and ends the hold. `undecided` (reason required) marks the hold and changes nothing else. An archive of a report-made hold is classified again by the facts and may be recorded as `kind_changed`.
- **`memory.heldSettle`** `{ id, action: archive | release | reoffer, reason, project?, if_awaiting? }`: `if_awaiting: true` is a compare-and-set: the hold is read again inside the write's transaction and the call is refused `E_PRECONDITION { id, awaiting: false, state, held_row }` unless it is active AND awaits the operator (`notes-held.isAwaiting`, the predicate behind `memory.held { awaiting }`: `undecided.rev` equals the hold's `rev`). A re-offer clears `undecided` and leaves the hold active, so without the flag a second settle on the note still writes; with it, it does not (the panel always passes it). The explicit operator only (`E_ROLE` for a tool call and for the operator on the harness channel). Returns the rows it changed.
- **`memory.noteRestore`** of a note archived with unsettled reports writes a fresh reported hold in the same transaction (`held` in the answer, `restored_from` on the hold); the explicit operator may pass `settle_reports: true` to settle them instead. A restore to pending writes no hold.
- **`memory.noteVerdicts`** report verdicts take an optional `report` (the key as listed), judge one report each, and are recorded as advice on the hold (`report_verdicts`, raising its revision), never archiving or releasing. A task reviewer's note verdict on a held note is advice too (`note_verdicts`; the answer entry has `advice: true`). The `reviewBrief` reports carry `report.key`, `held` and `self_report`.
- **`E_HELD`**: every write that would change a held note's namespace, status, supersedes, body state or promotion, or delete it, is refused for anyone but the explicit operator and the archive review's cited outcome on that note. It is raised by the store (`memory.store`, `memory.setStatus`, `memory.noteResolve`, `memory.delete`, `memory.promote`, `memory.noteRestore`, `memory.noteVerdicts` are the methods that reach it). `detail: { id, held_row, op }`.
